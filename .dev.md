# AzHST development notes

## Debug-only authentication test overrides

Debug builds recognize two presence-based environment variables for testing
the GitHub authentication UI:

| Variable | Debug behavior |
|---|---|
| `TEST_NO_GH_SIGNIN` | Skips the GitHub account check during application startup and starts in the signed-out state. The user can still open the manual sign-in instructions and confirm completion; that confirmation performs the normal account check. |
| `TEST_NO_GH_BIN` | Simulates GitHub CLI being unavailable. Every account check returns the normal missing-`gh` status without starting a `gh` process. |

These overrides are compiled only when the application is built with the
`Debug` configuration. Release builds ignore both variables and do not read
them. Only presence matters; the value is not parsed. `TEST_NO_GH_BIN` takes
precedence when both variables are present.

PowerShell examples:

```powershell
$env:TEST_NO_GH_SIGNIN = "1"
dotnet run --project .\src\AzHST.Desktop\AzHST.Desktop.csproj --configuration Debug
Remove-Item Env:\TEST_NO_GH_SIGNIN
```

```powershell
$env:TEST_NO_GH_BIN = "1"
dotnet run --project .\src\AzHST.Desktop\AzHST.Desktop.csproj --configuration Debug
Remove-Item Env:\TEST_NO_GH_BIN
```

The variables are test controls only. They are not saved to `settings.json`
and must not alter Release authentication behavior.

## Command-line startup modes

AzHST supports one application-specific command-line argument:

| Argument | Behavior |
|---|---|
| `--portable` | Uses executable-adjacent directories for AzHST-owned writable data and the default generated output. |

No other AzHST-specific command-line arguments are currently supported. The
argument match is exact and case-sensitive. All startup arguments continue to
be passed to Avalonia.

`ApplicationLaunchOptions` reads the arguments exposed by
`IClassicDesktopStyleApplicationLifetime`. The composition root then selects
one of the two `ApplicationPaths` factories:

| Path | Standard startup | `--portable` startup |
|---|---|---|
| Data root | `<LocalApplicationData>\AzHST` | `<application-directory>\data` |
| Settings | `<data-root>\settings.json` | `<application-directory>\data\settings.json` |
| Project history | `<data-root>\projects.db` | `<application-directory>\data\projects.db` |
| Copilot SDK data | `<data-root>\copilot` | `<application-directory>\data\copilot` |
| Sample queries | `<working-directory>\data\azhst.db` | `<application-directory>\data\azhst.db` |
| Default generated output | `<working-directory>\generated` | `<application-directory>\generated` |

The portable application directory is `AppContext.BaseDirectory`, not the
process working directory. Portable mode is intended for a self-contained
archive extracted to a writable directory; installed directories such as
Windows `Program Files`, signed macOS application bundles, and system-managed
Linux locations may be read-only. Bundled resources remain under
`<application-directory>\resources` in both modes.

Standard and portable startup use separate data stores. AzHST does not
automatically migrate or merge settings, projects, generated files, or Copilot
sessions between them. A custom output directory selected in **Settings**
continues to override the mode's generated-output default. GitHub CLI
authentication is owned by `gh` for the operating-system user and is never
copied into portable data.

Run portable mode from an extracted build:

```powershell
.\AzHST.Desktop.exe --portable
```

When running through `dotnet run`, use `--` to separate `dotnet` options from
AzHST arguments:

```powershell
dotnet run --project .\src\AzHST.Desktop\AzHST.Desktop.csproj --configuration Release -- --portable
```

## Local sample query database

AzHST stores home-page sample questions in:

```text
data\azhst.db
```

Standard startup resolves this path from the working directory, matching the
standard `generated\` artifact default. Portable startup resolves it under the
executable-adjacent `data\` directory. Runtime database files and SQLite WAL
sidecars are ignored by Git.

`SqliteSampleQueryRepository.InitializeAsync()` runs during main-window
startup. For an existing file it verifies:

- SQLite `quick_check`
- AzHST's SQLite `application_id`
- schema `user_version`
- required table and column names
- foreign-key integrity
- the stored ISO-8601 generation timestamp

Corrupt, non-SQLite, or incompatible-schema files are deleted and recreated.
Lock, permission, disk, and other environmental failures are surfaced instead
of being treated as corruption.

Schema version `1` contains:

| Table | Purpose |
|---|---|
| `categories` | Stable category ID, display name, description, and order |
| `sample_queries` | Ten query texts per category with creation timestamp |
| `metadata` | `sample_queries_generated_utc` freshness timestamp |

The six category IDs are:

```text
service-explanation
comparison
architecture-design
lifecycle
decision-guide
implementation-overview
```

A new or reset database is seeded with ten curated queries per category so the
home page works without network access. Each time the home page is entered,
AzHST selects four random categories and one random query from each.

If the stored generation timestamp is at least seven days old, an authenticated
startup or return to Home asks Copilot automatic model selection for exactly
ten new queries per category. The application rejects missing categories,
extra or duplicate questions, empty values, and oversized text. It then
replaces categories, questions, and the timestamp in one SQLite transaction.
Generation failures preserve the previous set and leave the old timestamp in
place so a later startup or Home visit can retry.

## Local project workspace

User projects are stored separately from the resettable sample-query catalog:

```text
<data-root>\projects.db

<configured-output>\
  <project-id>\
    000\
      index.html
      presentation.pptx
```

The standard data root is `<LocalApplicationData>\AzHST`; portable mode uses
`<application-directory>\data`. `SqliteProjectRepository` creates schema
version `1` with:

| Table | Purpose |
|---|---|
| `projects` | Project title, original question, explicit Copilot session ID, timestamps, and last-used model/theme IDs |
| `project_revisions` | Composite project/revision key, generated file paths, generation status, and update timestamp |

The current product always uses revision ID `000`. The composite key and
revision directory remain explicit so immutable history can be added later
without changing the project boundary.

Project and revision IDs are validated as portable single path segments.
Validation rejects both `/` and `\`, control characters, Windows-reserved
filename punctuation, and trailing spaces or periods on every operating
system.

Unlike `data\azhst.db`, `projects.db` contains user history and is never
automatically reset. Startup validates its application ID, schema version,
table shape, integrity, and foreign keys. Corrupt or incompatible databases
produce a visible error while preserving the original file.

Each project owns one explicit GitHub Copilot SDK session ID. Initial
generation creates that session, while follow-up refinement calls
`ResumeSessionAsync` with the same ID. The SDK shared cross-session search
store remains disabled, tools remain empty, and disposing a session does not
delete its persisted transcript. Project deletion explicitly deletes the SDK
session, generated project directory, and database row.

Initial visualization generation and follow-up refinement each allow up to
five minutes for `SendAndWaitAsync` to return a complete HTML page. Only an SDK
`TimeoutException` is reported as a timeout. User cancellation is surfaced as
cancellation, while authentication, model, runtime, and other SDK failures
retain their original error chain.

`FileProjectArtifactStore` writes a temporary file in the revision directory
and moves it over `index.html` only after the complete HTML has been validated
and secured. A failed or cancelled follow-up leaves the existing HTML
unchanged. A successful follow-up clears the recorded PowerPoint association;
the next **Build PowerPoint** operation replaces the deck and records its path
again.

## Application identity and CI release flow

The Desktop project owns the user-facing application identity:

```xml
<AppName>AzHST</AppName>
<Product>$(AppName)</Product>
<AssemblyTitle>$(AppName)</AssemblyTitle>
<Version>0.0.0</Version>
```

`0.0.0` is the local and non-release fallback. Release CI must override the
standard `Version` property rather than editing the project file. The main
window reads `AssemblyProductAttribute` and
`AssemblyInformationalVersionAttribute` from the built Desktop assembly, so
the application name and displayed version are never duplicated in XAML.
Build metadata after `+`, such as a commit SHA, remains available in the
assembly but is omitted from the normal UI display.

### Release source of truth

Use an annotated or protected Git tag such as `v1.0.0` as the release version
source. A release workflow should:

1. Trigger only for tags matching the repository's release convention.
2. Validate the tag as semantic version text.
3. Remove the leading `v` to obtain the build version.
4. Publish every target with the same `Version`.
5. Let the .NET SDK append the source revision to `InformationalVersion`.
6. Pass the same version to the platform packaging step.
7. Sign the final package where signing is configured.
8. Upload versioned artifacts and checksums to the GitHub release.

Example PowerShell used by a GitHub Actions step:

```powershell
$tag = "${{ github.ref_name }}"
if ($tag -notmatch '^v(?<version>\d+\.\d+\.\d+(?:-[0-9A-Za-z.-]+)?)$') {
    throw "Release tag '$tag' is not a supported semantic version."
}

$version = $Matches.version
"version=$version" >> $env:GITHUB_OUTPUT
```

Publish using the normalized outputs:

```powershell
dotnet publish .\src\AzHST.Desktop\AzHST.Desktop.csproj `
  --configuration Release `
  --runtime win-x64 `
  --self-contained true `
  -p:Version="${{ steps.version.outputs.version }}" `
  -p:ContinuousIntegrationBuild=true
```

The SDK records an informational version such as
`1.0.0+<source-revision>`. AzHST displays `1.0.0` and leaves the complete value
in assembly metadata for diagnostics.

Do not independently assign `AssemblyVersion` or `FileVersion` unless the
project later adopts a specific binary-compatibility policy. The .NET SDK
derives compatible numeric values from `Version`.

### Artifact names

The packaging step must consume the same normalized version output; it must
not parse the version back out of the executable. Use consistent names that
include the product, semantic version, platform, and architecture:

```text
AzHST-1.0.0-win-x64.zip
AzHST-1.0.0-linux-x64.tar.gz
AzHST-1.0.0-osx-x64.tar.gz
AzHST-1.0.0-osx-arm64.tar.gz
```

The current CI workflow produces these self-contained portable archives plus a
matching `.sha256` file. It does not claim to produce a native installer:
installer signing and packaging tools have not been configured yet. When that
tooling is added, use equally explicit native package names such as:

```text
AzHST-1.0.0-win-x64-setup.exe
AzHST-1.0.0-osx-arm64.dmg
AzHST-1.0.0-linux-x64.AppImage
```

Managed assemblies are published as a compressed single-file executable.
Native libraries and the GitHub Copilot runtime remain physical sidecars.
Do not enable `IncludeNativeLibrariesForSelfExtract`: the Copilot SDK resolves
its runtime wrapper from `runtimes\<rid>\native` beside the application.
`AzHST.Infrastructure` is not RID-agnostic so cross-RID publishing propagates
the requested target and packages the matching Copilot runtime.

Prerelease and CI labels remain in archive names:

```text
AzHST-1.1.0-beta.1-win-x64.zip
AzHST-0.0.0-ci.123-linux-x64.tar.gz
```

Branch and pull-request builds use a non-release `0.0.0-ci.<run-number>`
version. They may be retained as workflow artifacts for verification, but they
must not be published as release installers.

## Embedded application documents

The Desktop project embeds the repository documents with stable logical names:

```xml
<EmbeddedResource Include="..\..\ABOUT.md"
                  LogicalName="AzHST.About.md" />
<EmbeddedResource Include="..\..\RELEASE-NOTES.md"
                  LogicalName="AzHST.ReleaseNotes.md" />
```

`AboutDialogService` loads both resources from `AzHST.Desktop.dll` whenever
the About dialog opens. `EmbeddedMarkdownDocumentLoader` converts the Markdown
with Markdig advanced extensions and raw HTML disabled. It wraps the output in
a standalone dark-theme document with a restrictive Content Security Policy.

The **About** tab displays the embedded concise `ABOUT.md` and the
**Changelog** tab displays the embedded release notes. Selected public sections
in `ABOUT.md` are kept identical to `README.md` by a repository test. HTTP and
HTTPS links are opened through the operating system's default browser; other
navigation is blocked. When `WebViewAvailability` reports that no adapter is
available, the dialog shows the original embedded Markdown as selectable text.

When adding another documentation tab:

1. Add the source file as an `EmbeddedResource` with a stable logical name.
2. Load it through `EmbeddedMarkdownDocumentLoader`.
3. Add an `AboutTabViewModel` to the `Tabs` collection.
4. Reuse the shared tab content and HTML document templates.
5. Verify the resource name in a published build as well as a normal build.

## Application icon assets

AzHST uses an original connected-node letter `A` rather than an official Azure
service mark. The source and generated assets are:

```text
src\AzHST.Desktop\Assets\
  azhst-icon.svg
  azhst-icon.png
  azhst-icon.ico
```

- `azhst-icon.svg` is the editable vector source for future packaging.
- `azhst-icon.png` is the 512-by-512 portable raster asset.
- `azhst-icon.ico` contains Windows sizes from 16 through 256 pixels and is
  configured as the executable icon.

All Avalonia windows use the packaged ICO for their window and taskbar icon.
The main-window sidebar deliberately shows the product name without a separate
logo badge so branding does not consume navigation space.

### Action button icons

Every non-common action button uses a `PathIcon` alongside its text. Shared
16-by-16 vector geometries are defined once in `App.axaml`, inherit the
button's foreground color, and use eight pixels of spacing before the label.
Buttons that perform common dialog dismissal actions, such as **Cancel**,
**OK**, or **Close**, may remain text-only. Icon-bearing buttons must retain a
clear text label and an explicit accessible name where the action is not
already unambiguous.

## Output theme configuration

AzHST keeps output theme requirements in validated JSON files. Settings store
only the selected theme IDs. Theme files contain declarative colors,
typography, appearance, and motion values; they never contain arbitrary CSS,
JavaScript, PresentationML, or prompt text.

The same settings file stores the selected GitHub Copilot model ID. The
Settings dialog obtains account- and policy-specific choices from
`ICopilotModelCatalog`; `auto` is always available and remains the default.
Query assessment and HTML generation use that selection. New HTML already
contains its PowerPoint narrative, while legacy HTML uses the selection for
fallback presentation planning.

Theme definitions intentionally have **no theme `version` property**.
`schemaVersion` identifies the parser contract only. The current supported
schema is `1`, and unknown JSON properties are rejected.

### Files and defaults

```text
resources\
  themes\
    html\
      azure-night.json
    presentation\
      professional-light.json
      professional-night.json
```

The Desktop project copies this directory to
`resources\themes` beside the application executable. The composition root
loads it through `FileOutputThemeCatalog.CreateDefault()`.

Default selections:

| Output | Theme ID |
|---|---|
| HTML visualization | `azure-night` |
| PowerPoint presentation | `professional-night` |

Bundled PowerPoint choices:

| Theme ID | Display name | Intended use |
|---|---|---|
| `professional-light` | Professional Light | Bright rooms, printed material, and general-purpose presentations |
| `professional-night` | Professional Night | Dark presentation decks, screen sharing, and low-light environments |

The user can change both selections in **Settings**. The selected IDs are
persisted in `settings.json`:

```json
{
  "model": "auto",
  "themes": {
    "htmlThemeId": "azure-night",
    "presentationThemeId": "professional-night"
  }
}
```

Missing or blank model and theme IDs from older settings files are normalized
to the defaults. A selected model that is no longer returned by Copilot is
identified when Settings loads and reset to Automatic when saved. A theme ID
that is present but unavailable in the catalog produces an explicit
configuration error when that output is generated.

### Shared validation

Every theme must provide:

- `schemaVersion`: integer `1`
- `id`: lowercase letters, digits, and hyphens; must match
  `[a-z0-9][a-z0-9-]{0,63}`
- `displayName`: non-empty, at most 80 characters, with no control characters

Additional rules:

- JSON must deserialize strictly; unknown properties are errors.
- Each output-kind directory must exist and contain at least one `.json` file.
- IDs must be unique within the HTML or presentation catalog.
- Colors must use `#RRGGBB`.
- Font-family values permit only letters, digits, spaces, commas, periods,
  apostrophes, quotation marks, underscores, and hyphens.
- Required text/background combinations must meet a WCAG contrast ratio of
  at least `4.5:1`.

| Property | Validation |
|---|---|

Theme motion values control timing and whether the Copilot prompt may permit
continuous decorative motion; they do not weaken the accessibility baseline.

### HTML application

`CreateProjectUseCase` and `RefineProjectUseCase` resolve the selected theme
before generation. The typed values are converted into trusted Copilot
requirements; no free-form theme prompt is loaded from JSON.

After Copilot returns HTML, `GeneratedHtmlDocumentProcessor`:

1. Removes any model-provided `style#azh-output-theme`.
2. Replaces any existing `data-azh-theme` attribute.
3. Adds `data-azh-theme="<selected-id>"` to the root `<html>` element.
4. Injects an authoritative `style#azh-output-theme` after model styles.
5. Applies the selected page background, text, typography, color scheme, and
   focus baseline.

--azh-surface-raised
--azh-surface-selected
--azh-border
--azh-text
--azh-text-muted
--azh-primary
--azh-flow-active
--azh-accent
--azh-success
--azh-warning
--azh-danger
--azh-focus
--azh-icon-tile
--azh-font-family
--azh-base-size
--azh-line-height
--azh-corner-radius
--azh-icon-tile-size
--azh-transition-duration
--azh-sequence-step-duration

Copilot is instructed to consume these variables rather than redefine them.

### PowerPoint application

`GeneratePresentationUseCase` resolves the selected presentation theme after
the Copilot slide plan has passed validation. `OpenXmlPresentationBuilder`
maps the typed theme to native DrawingML colors, fonts, sizes, card geometry,
header treatment, icon tiles, connectors, and the package theme.

Geometry, slide bounds, connector routing, arrow direction, and Office package
structure remain deterministic code. JSON cannot inject Open XML.

### PowerPoint planning and layout contract

Every newly generated visualization contains exactly one non-executable
`<script id="azh-presentation-plan" type="application/json">` manifest. The
HTML generator creates this manifest with the visible page so both outputs use
the same parent section labels, nested headings, explanatory paragraphs,
callouts, nodes, relationships, progressive states, scenarios,
recommendations, caveats, and structured source titles/URLs.
`GeneratedHtmlDocumentProcessor` requires valid JSON and does not count this
data block as the page's interactive JavaScript.

The top-level manifest `sources` array contains 1-10 validated official
Microsoft HTTPS references. The visible final HTML `Sources` section must
contain exactly one `data-azh-source` link for every manifest entry, with the
same title, URL, and order plus `target="_blank"` and
`rel="noopener noreferrer"`. Other external links and all external resources
remain prohibited. Embedded-preview source links open in the system browser.

PowerPoint generation reads that embedded plan directly and validates it using
the normal presentation contract; it does not ask a second model call to
reinterpret new pages. For older saved HTML without a manifest, Infrastructure
falls back to a maximum 60,000-character AngleSharp outline in document order.
That fallback includes visible titles, headings, paragraphs, list and
definition items, table rows, controls, section labels, SVG labels, grouped
`data-node` content, scenario options, and bounded human-readable interaction
steps or state text extracted from inline JavaScript. It never executes scripts
or sends embedded data-URI bytes to Copilot.

The Desktop command is gated by the available preview rather than the current
GitHub-authentication flag because manifest-backed builds are local. Legacy
fallback failures from Copilot are wrapped with sign-in/model guidance. UI
progress callbacks are operation-scoped so queued updates cannot overwrite the
final success, cancellation, or failure state; complete nested error messages
and the last reported stage remain visible in a selectable error panel.

The structured plan supports these slide kinds:

| Kind | Purpose | Connections |
|---|---|---|
| `diagram` | Architecture, request flow, lifecycle, or ordered process | At least one |
| `comparison` | Side-by-side options or services | None |
| `cards` | Features, recommendations, trade-offs, risks, or caveats | None |
| `content` | Limited supporting text | None |
| `summary` | Limited closing text | None |

Each slide can carry `sectionTitle`, `title`, `subtitle`, `summary`, and
`callout`. The renderer keeps those levels distinct: the parent section appears
above the slide title, nested headings and explanations share the narrative
area, and warnings or operational notes receive separate callout emphasis.
Duplicate section/title values are collapsed during validation. Every bounded
model-generated display field is shortened at a safe word boundary with an
ellipsis when necessary instead of failing the entire PowerPoint build. This
includes presentation and slide titles, subtitles, summaries, callouts,
bullets, source titles, node labels and details, and connection labels.
Required text must still be present; slide counts, node IDs, relationships,
icon keys, source URLs, and other structural contracts remain strict.

Every plan has 4-9 content slides. The renderer adds the title slide and a
final standalone `Resources / Sources` slide from the top-level source
contract. Sources render as compact numbered bibliography entries with the
reference title and URL; all validated top-level references, up to the
10-source contract maximum, are retained. Per-slide provenance can cite the
same complete source set. The slide never refers to HTML or the conversion
process.
The first content slide must be `diagram`, `comparison`, or `cards`, and at
least two thirds of all content slides must use one of those visual kinds.
Visual slides contain at least two nodes and no bullets. Content and summary
slides contain no nodes or connections and render each bullet as a separate
editable numbered card rather than one large text box.

Diagram slides contain no more than six nodes. Larger interactive stages are
represented by a concise forward-path overview followed by numbered state
slides for branches, responses, failures, rollback, or alternate outcomes.
This keeps node explanations readable and avoids ambiguous return connectors.

Each node has one semantic `tone`: `primary`, `accent`, `success`, `warning`,
`danger`, or `neutral`. The renderer maps tones to the selected theme through
the aligned card outline and icon treatment without adding a detached accent
strip. Short ordered diagrams and comparisons use a horizontal layout; larger
visual sets use a bounded grid. Compact rows have a maximum card width, and an
incomplete final grid row is centered instead of left aligned.

Adjacent nodes can use direct edge-to-edge connectors. Cross-row and
non-adjacent connections use editable orthogonal line segments routed through
the space between cards; only the final segment has an arrowhead. A concise
connection label is rendered only when it fits safely on a horizontal segment,
otherwise it is omitted. Generated text boxes use DrawingML automatic fitting,
and long source URLs are fitted inside editable cards on the final slide. Only
the title slide contains the generated-by/artifact footer; content and source
slides do not contain footers.

PowerPoint animation is intentionally unsupported. When the HTML has
interactive scenarios, selected request paths, failure modes, or progressive
steps, the planner represents those states as adjacent visual slides.

## Adding a theme

1. Copy an existing definition in the matching directory.
2. Give it a unique stable `id` and user-facing `displayName`.
3. Change only typed schema values; do not add a theme `version` property.
4. Keep every color in `#RRGGBB` form and satisfy contrast requirements.
5. Run:

   ```powershell
   dotnet test .\tests\AzHST.Infrastructure.Tests\AzHST.Infrastructure.Tests.csproj
   dotnet test .\tests\AzHST.Application.Tests\AzHST.Application.Tests.csproj
   ```
